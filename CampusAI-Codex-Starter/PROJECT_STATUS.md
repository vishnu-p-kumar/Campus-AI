# CampusAI project status

## Overall state

The initial health-check milestone has expanded into a working full-stack capstone application. Core student, placement staff, document/RAG, resume/interview, administration, and research workflows are implemented in source and have local automated coverage. The project is **in progress**, not complete. Cloud deployment and provider-backed behavior still need external integration verification.

## Implemented

- [x] Placement assistant uses a dedicated `GEMINI_PLACEMENT_API_KEY`, distinct from resume and interview credentials. Admin-approved document chunks are retrieved by content and filename, and each complete selected chunk is sent with its filename/page/section metadata to Gemini. When retrieved document evidence is insufficient, Gemini URL Context can read only the exact public HTTPS URLs entered by the administrator (up to 20 per request); it does not follow nested links, and only successfully retrieved approved URLs can be cited. Citations and numeric claims are validated, and unsafe/unavailable answers abstain.

- [x] Next.js App Router interface, responsive shell, authentication forms, student workflows, placement staff and admin surfaces.
- [x] FastAPI API, PostgreSQL-compatible SQLAlchemy setup, SQLite local mode, Alembic history and readiness checks.
- [x] Student registration/login, role authorization, access/refresh tokens, password reset flow, staff provisioning CLI, account deletion and audit records.
- [x] Account deletion explicitly removes student-owned profiles, applications, notifications, chat/resume/interview content, and tokens independent of SQLite FK settings; audit references are anonymized and historical placement outcomes are retained with the student link removed.
- [x] Shared authentication throttling through atomic database upserts, with HMAC-keyed client identifiers and a per-minute configurable limit.
- [x] Refresh token rotation consumes the prior token with a conditional atomic database update that rechecks both revocation and expiry, so a token expiring between lookup and update cannot be accepted and parallel refresh requests cannot both rotate it.
- [x] Password reset tokens are consumed with a conditional atomic update that rechecks use and expiry, preventing concurrent reuse and expiry-time races.
- [x] Student profile/dashboard, company management and versioned requirements, placement drives, application status/outcomes and deterministic eligibility explanations.
- [x] Eligibility checks confirm the linked criteria document is still approved; superseded or rejected source documents return manual verification across company checks, dashboards, eligible rosters, and application submission.
- [x] A unique database constraint prevents duplicate applications, and concurrent uniqueness conflicts return a clear HTTP 409. PostgreSQL race coverage expects one successful application and 31 conflicts.
- [x] Placement application status transitions use a PostgreSQL row lock and refresh the locked state before emitting notifications or placement records, preventing concurrent duplicate side effects. A PostgreSQL serialization test is configured in CI.
- [x] Placement application eligibility locks and reloads its company requirement row and approved source-document scope on PostgreSQL; document approval/rejection and the application eligibility check serialize on the same scope lock. Rejection is allowed only while review is pending.
